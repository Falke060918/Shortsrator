# releases — 버전 규칙과 노트 형식

이 템플릿의 버전별 변경 기록 자리다. 노트 1건은 `docs/releases/<major>.<minor>.x/<x.y.z>.md`이고, 이 README는 규칙만 담는다.

`docs/`는 `template-update.sh`의 HARD EXCLUSIONS라 **릴리즈 노트는 파생 프로젝트로 전파되지 않는다** — 템플릿 원본에만 쌓이는 기록이다. 파생 프로젝트 쪽에서 "무엇이 바뀌었나"를 알고 싶으면 이 저장소를 직접 본다.

## 버전 규칙 (semver 기반, 현재 0.x = 초기 단계)

이 저장소에 "제품 기능"은 없다. 버전이 세는 대상은 **규칙 문서(CLAUDE.md·`.claude/agents/`)·스킬·훅/설정·문서 기계장치(`scripts/`)**의 변경이다.

- **minor (0.x.0)** — 파괴적 변경. 파생 프로젝트가 `/template-update` 후에도 **손을 대야** 하는 것: 규칙의 의미가 뒤집히거나(기존 동작 금지·의무 신설), 스킬·명령이 없어지거나 이름이 바뀌거나, 훅/설정 키가 바뀌어 재시작·재설정이 필요하거나, `template-update.sh`의 동기화 경로·HARD EXCLUSIONS가 바뀔 때.
- **patch (0.0.x)** — 기존 규칙을 깨지 않는 추가·보강·버그 수정. 스킬 신설, 규칙 문구 강화, 스크립트 수정, GOTCHAS 등재 수준.
- **major** — 1.0 이전에는 올리지 않는다. 0.x 전체가 초기 단계이며, 파괴적 변경도 minor로 흡수한다.
- 애매하면 **낮은 쪽**을 고른다. 파생 프로젝트가 아무것도 안 해도 되면 patch다.
- 문서 오타·서식·산문 다듬기만이면 **버전을 올리지 않는다** — 노트도 쓰지 않는다.

## 폴더 규칙 (버전 하위 폴더는 필수)

노트는 `docs/releases/` 바로 아래에 두지 않는다. **`<major>.<minor>.x/` 폴더를 만들어 그 안에 넣는다.**

- `0.0.x/` 폴더가 `0.0.1.md`, `0.0.2.md`, … 를 담는다. 버전이 `0.1.0`에 들어가면 거기서 끝난다.
- `0.1.0`부터는 `0.1.x/` 폴더가 새로 생겨 `0.1.0.md`, `0.1.1.md`, … 를 담는다. `1.0.x/`, `1.1.x/`도 같은 방식이다.
- 예: `docs/releases/0.0.x/0.0.3.md` · `docs/releases/0.1.x/0.1.0.md` · `docs/releases/1.0.x/1.0.2.md`
- 폴더가 없으면 만들고, 기존 폴더에 다음 번호를 이어 넣는다. 지난 폴더로 거슬러 올라가 노트를 추가하지 않는다.

## 노트 1건의 형식 (상한 60줄)

상한은 60줄이다. 넘으면 항목당 문장을 늘리는 게 아니라 **항목 수를 추린다** — 필드는 각각 정확히 1줄이다. 히스토리는 git에 남으므로 과감히 압축한다.

개선 항목 하나는 **고유 코드가 붙은 제목 + 한 줄짜리 세 필드**다. 이 셋 외의 필드를 넣지 않고, 추가/변경/수정 같은 분류로 묶지도 않는다.

제목에 `(기준선)`을 붙일 수 있다 — **이번에 바꾼 게 아니라 원래부터 있던 기능을 처음 기록해 두는 항목**이라는 표시다. 첫 릴리즈처럼 이전 기록이 없는 노트에서만 쓰고, 쓰는 노트에는 이 뜻을 한 줄로 적어둔다.

```markdown
# <x.y.z> — YYYY-MM-DD

<한 줄 요약: 이 버전이 무엇을 바꿨나>

## [RN-0001] 한 줄 제목

- 기존: 지금까지는 어땠는지
- 페인포인트: 그래서 뭐가 불편했는지
- 개선: 이번에 어떻게 바뀌었는지

## [RN-0002] 한 줄 제목

- 기존: …
- 페인포인트: …
- 개선: …

## 파생 프로젝트 영향

<`/template-update` 후 사용자가 해야 할 일. 없으면 "없음 — 동기화만 하면 된다.">
```

### 고유 코드 규칙

- 코드는 **저장소 전체에서 하나뿐이고 단조 증가**한다 — `RN-0001`, `RN-0002`, `RN-0003`, … 4자리 0채움.
- **버전이 올라가도 절대 초기화하지 않고, 이미 쓴 번호를 다시 쓰지 않는다.** `0.0.9.md`가 `RN-0042`로 끝났으면 `0.1.0.md`는 `RN-0043`부터다.
- 다음 번호는 **기존 노트 전체를 훑어 가장 큰 RN 코드를 찾고 +1** 한다(`docs/releases/` 전 폴더 대상, 예: `rg -oI -g '!README.md' "RN-[0-9]{4}" docs/releases | sort | tail -1`). `-I`(파일명 제외)와 `-g '!README.md'`(이 README의 예시 코드 제외)를 빼면 예시가 최대값으로 잡혀 번호가 통째로 건너뛰어진다. 별도의 카운터 파일은 두지 않는다.
- 한 번 발행한 항목의 코드는 고치지 않는다 — 나중에 그 코드로 지목해 이야기하기 위한 번호다.

### 말투 규칙 — **개발자가 아닌 사람이 읽는다**

- 파일 경로·함수 이름·내부 용어를 쓰지 않는다. 꼭 필요한 용어는 괄호로 뜻을 붙인다(예: "변경 기록(릴리즈 노트)").
- 세 필드는 각각 **한 줄**이다. 무엇이 불편했고 그래서 무엇이 편해졌는지가 읽는 사람 입장에서 드러나야 한다.
- **`## 파생 프로젝트 영향`은 뺄 수 없다** — 없으면 "없음"이라고 적는다. 제목은 이대로 두되, 본문에서 파생 프로젝트(이 템플릿을 복사해 만든 다른 프로젝트)의 뜻을 한 번 풀어준다.
- 절대 경로와 OS 전용 명령은 적지 않는다(그 자리는 `docs/MACHINE.md`다).
- 한국어로 쓴다 — 사용자가 읽는 문서다.

## 발행 시점

`/handoff`가 판단한다 — 이번 세션 변경이 규칙·스킬·설정에 영향을 줬을 때만 버전을 올리고 노트를 STATE.md와 **같은 커밋**에 넣는다. 매 핸드오프마다 발행하지 않는다.
