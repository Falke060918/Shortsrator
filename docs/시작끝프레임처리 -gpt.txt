미지원이면 4번 컷의 요구사항을 없애지 말고, 해당 컷만 다른 API로 라우팅하는 게 맞습니다.

현재 Higgsfield 웹/Cinema Studio에는 Start + End Frames 기능이 명확히 존재합니다. Higgsfield는 2026년 현재 자동화 접근용으로 MCP/CLI도 제공하고 있지만, 이 인터페이스에서 Start/End 파라미터가 노출되는지는 실제 스키마 확인이 필요합니다.

제가 권하는 우선순위

A. Higgsfield API/MCP/CLI가 지원
→ 그대로 사용.

start_image
+ end_image
+ motion_prompt
→ video

B. Higgsfield 자동화 인터페이스가 미지원
→ 4번 컷만 Kling API로 fallback.

이게 제일 좋습니다. 현재 fal.ai의 Kling V3 계열 Image-to-Video API는 실제로 start_image_url/image_url과 end_image_url을 받을 수 있습니다. 즉 우리가 원하는 구조를 API로 그대로 자동화할 수 있습니다.

구조는:

CUT 1 → Higgsfield
CUT 2 → Higgsfield
CUT 3 → Higgsfield


CUT 4
start + end 필요
↓
Higgsfield capability check
↓
지원 → Higgsfield
미지원 → Kling API


CUT 5 → Higgsfield

이게 가장 깔끔합니다.

그래서 코드도 처음부터 provider 종속으로 만들면 안 됩니다

4번 컷을 이렇게 정의합니다.

generation_mode:
  start_end_video


start_image:
  xxx.png


end_image:
  yyy.png


prompt:
  camera moves...


duration:
  5

그리고 아래쪽에서:

start_end_video
        ↓
Provider Router
        ↓
Higgsfield available?
   YES → Higgsfield
   NO  → Kling

즉 “Higgsfield Start/End 기능”이 아니라 “Start/End Video라는 우리 시스템 기능”으로 정의하는 겁니다.

이렇게 만들어두면 나중에 Veo, Seedance 등 더 좋은 API가 나오더라도 provider 하나만 갈아끼우면 됩니다.

Kling까지 쓰고 싶지 않은 경우

그때는 single-frame I2V 두 개를 이어붙이는 fallback을 씁니다.

다만 단순 crossfade는 추천하지 않습니다.

예를 들어 시작 이미지가 A, 끝 이미지가 B라면:

A
↓
Image-to-Video #1
↓
카메라가 구조물 안으로 빠르게 접근
↓
벽 / 어둠 / motion blur로 화면 가림

그리고 B에서는 반대로 생성합니다.

B 이미지
↓
Image-to-Video #2


"camera rapidly pulls backward
from inside the structure..."

생성된 #2 영상을 reverse합니다.

그러면:

A
↓
push-in
↓
██████   ← occlusion / blur
↓
reverse된 B 영상
↓
B

가 됩니다.

결과적으로 Start/End interpolation은 아니지만 시청자 입장에서는 A에서 B로 카메라가 이동한 것처럼 보일 수 있습니다.

건축/구조 설명 영상에서는 특히 잘 먹힙니다.

예:

건물 외관
→ 창문으로 빠르게 진입
→ 검은 프레임
→ 내부 구조

또는

교량 전체
→ 교각으로 zoom
→ concrete surface fills frame
→ 단면 구조 등장

이런 식입니다.

피해야 할 fallback

A 영상 생성 + B 영상 생성 + 그냥 dissolve

이건 하지 않는 게 좋습니다.

A ──── fade ──── B

바로 슬라이드쇼/AI 영상 느낌이 납니다.

Start/End 컷을 사용하는 이유 자체가 공간적 이동 또는 변형의 연속성을 만드는 것이기 때문에, fallback에서도 최소한 다음 중 하나는 있어야 합니다.

object occlusion
motion blur
whip movement
zoom-through
darkness
smoke/dust
surface close-up
flash

즉 숨길 프레임을 하나 만든 뒤 그곳에서 splice하는 겁니다.

최종 결정안

파일럿 설계 문서에는 이렇게 박아두는 게 좋습니다.

4번 컷은 Start+End Frame Video를 기본 생성 방식으로 사용한다.

Higgsfield 자동화 인터페이스에서 Start/End Frame 지원 여부를 구현 1일차에 확인한다.
지원 시 Higgsfield를 사용한다.
미지원 시 해당 컷에 한해 Kling Start/End Image-to-Video API로 자동 fallback한다.
외부 provider까지 실패할 경우에만 2× single-frame I2V + occlusion splice 방식으로 대체한다.
수동 Higgsfield 웹 생성은 파일럿 검증에는 허용하지만 운영 자동화에는 포함하지 않는다.

저라면 이걸 채택합니다.

특히 Kling API fallback을 넣으면 이 문제는 사실상 blocker가 아닙니다. Start/End 자체를 포기할 이유가 없습니다. 현재 Kling V3 API 계열에는 end frame 입력이 이미 명시적으로 존재합니다.

그리고 장기적으로는 Higgsfield를 핵심 엔진으로 만드는 게 아니라 provider router 아래의 하나의 엔진으로 만드는 것이 중요합니다. 그래야 숏폼 자동화를 계속 개선할 수 있습니다.
